# Dolphin-NS2: Porting Plan

Research snapshot: 2026-11-14. The Switch 2 homebrew scene is weeks old and changes fast,
so check every link and version before relying on it.

## 0. Status (2026-11-14)
- `ounce-devkit` Docker image built (devkit 20261114: libounce 9382b1e, OunceVK f5afcd2, kaiHEN eb81e19).
  The compiler is devkitA64 GCC 15.2.0. C++20 builds with `<format>`, `std::thread` and exceptions.
  The `kaihen-jit.o` JIT provider is present, and so is `kaihenJitPublishRanges`.
- `vulkan-clear.nro` and `gles-triangle.nro` build. Neither has been tested on hardware yet.
- Sources are in `external/`: `ounce-devkit`, `kaihen`, `dolphin-nx` (v1.2.2, f13fdd6, GPLv2+, all submodules).
- Build anything with `tools/devkit.sh <cmd>` from anywhere in the project.
  The image needs `docker build --network=host` because Docker DNS fails on this host.

**Key finding for step 4:** `dolphin-nx/Source/Core/Common/MemoryUtil.cpp` calls `jitTransitionToExecutable`
**once** at allocation. After that it writes code through `jitGetRwAddr` forever, which relies on Switch 1's
true RW↔RX alias. On kaiHEN the RW pointer is a staging copy, so code written after allocation never reaches RX.
The port needs a publish call (`kaihenJitPublishRanges`) after each block is emitted or patched.
It must also accept whatever `jit.type` kaiHEN reports, because it currently rejects anything except `JitType_CodeMemory`.

### Switch 2 build of dolphin-nx (done, untested on hardware)
`tools/build-dolphin.sh` produces `external/dolphin-nx/build-switch2/Binaries/dolphin.nro` (~45 MB).
Run `git diff` in `external/dolphin-nx` to see the changes. Everything is gated on `DOLPHIN_SWITCH2` / `__SWITCH2__`, so Switch 1 builds are unchanged.
- `CMake/Toolchain-Switch2.cmake`: uses libounce's `Switch2.cmake`, with Cortex-A78C flags and `__SWITCH2__`.
- `CMakeLists.txt`, `CMake/SwitchDependencies.cmake`: OunceVK replaces the Mesa SDK zip. Deko3D, Switch 1 PGO and libelf are off. `-lkaihen` is linked.
- `Tools/Switch/prepare_ouncevk.sh` (runs at configure time): copies `libouncevk-gl.a` (NVK, Zink and EGL in one object)
  and localizes its 249 public `vk*` functions so they don't clash with Dolphin's global PFN variables.
  It exports `vk_icdGetInstanceProcAddr` and `vk_icdNegotiateLoaderICDInterfaceVersion`, so `VulkanLoader.cpp` needs no changes.
- **JIT:** `Arm64Emitter::FlushIcacheSection(rw, rx)` now calls `Common::PublishExecutableMemory`,
  which finds the `Jit` that owns the range and calls `kaihenJitPublishRanges`. The `JitType_CodeMemory` check is dropped on Switch 2.
  Every block emit, link and backpatch now costs one IPC round trip to RO. Batching these is the next performance step.
- `PoisonMemory` (cache clear) writes BRKs into staging but doesn't publish them. Old RX code can't be reached after a clear,
  but it isn't overwritten either.
- Small fixes: a local `eglResizeSurfaceMESA` typedef (missing from OunceVK's headers),
  and the forwarder NACP patch uses libounce's `lang_data` layout.
- The HOME Menu forwarder stub (`Data/Sys/fwd/hbl.nso`) is still built against **libnx** for Switch 1 and is regenerated by every build.
  Its install path probably doesn't apply on Switch 2.

### Diagnostics (on by default in `tools/build-dolphin.sh`; `DIAGNOSTICS=OFF` to drop)
`Common/SwitchDiagnostics.cpp` writes to `sdmc:/switch/dolphin/diag/`:
- `boot.log`: startup breadcrumbs, synced to the SD card after every line, plus memory, core-mask and kaiHEN session info. The previous run is kept as `boot.prev.log`.
- `stderr.log`: Mesa and Dolphin console log output.
- `crash.log`: written from the libnx exception handler in `Core/MemTools.cpp`.
Run `tools/symbolize.sh crash.log` to map its `dolphin.elf+0x…` offsets to functions and source lines. It needs the `dolphin.elf` from the same build.

*emulated-console behavior*. Platform work (build, JIT memory, graphics/input plumbing) is fine in our own fork.
Don't send AI-written changes upstream.

## 1. Choose a stack

There are two separate homebrew ecosystems right now. Only one can realistically run Dolphin.

| | **ouncebrew: kaiHEN + ounce-devkit** (recommended) | sw2-sdk (HBLauncher) |
|---|---|---|
| Base | libnx-compatible (`libounce`) on devkitPro devkitA64 | Its own freestanding ABI |
| libc / C++ | newlib + devkitA64 libstdc++ (inherited from devkitPro) | **No libc**, no dynamic linking, C templates only |
| Graphics | **OunceVK** = Mesa NVK, Vulkan 1.4; GL/GLES 3.1 via Zink; EGL | Raw Vulkan on a launcher-owned swapchain, plus GPUBrew shaders |
| JIT | **Yes**: libnx `Jit` API, backed by kaiHEN's `ro` service | None documented |
| Filesystem / net | libnx fs + sockets | Packaged assets only; no SD, no network |
| Output | `.nro` started from hbmenu | `code.bin` + `data.bin` at fixed addresses |
| Repo policy | — | README excludes emulators |

**Decision: build on kaiHEN + ounce-devkit.** Dolphin needs C++20, threads, a JIT, Vulkan and file access.
sw2-sdk provides none of these.

## 2. Tools to install

### Host (Linux)
1. **devkitPro pacman** plus `switch-dev` (devkitA64, the GCC toolchain for `aarch64-none-elf`).
   Check that its GCC version is new enough for Dolphin's C++20 code (`aarch64-none-elf-g++ --version`).
2. **ounce-devkit**: https://github.com/ouncebrew/ounce-devkit. Bundles libounce, OunceVK and libkaihen.
   ```bash
   sh install.sh            # run inside the ounce-devkit checkout
   ```
   You can use the Docker image instead: `docker build -t ounce-devkit .`
3. Build environment for CMake (Dolphin uses CMake):
   ```bash
   source $DEVKITPRO/switch2vars.sh
   aarch64-none-elf-cmake -S . -B build && cmake --build build
   ```
4. Portlibs: devkitPro Switch portlibs that only use libc and libnx (SDL2, zlib, etc.) work unchanged.
5. Optional: Docker or Podman. kaiHEN and OunceVK both build reproducibly in containers.

### Console
- **kaiHEN**: https://github.com/ouncebrew/kaihen. It is the homebrew enabler, hbmenu and JIT provider.
  To launch hbmenu, hold R while starting a native game (twice).
- Entry exploit: the ns2jb chain. **Firmware version matters.** Reports say ns2jb targets 23.0.1, was patched in 23.5.0,
  and conflicting reports have kaiHEN running on 26.0.1. **Do not update the console** until you have confirmed what your firmware supports.
- ⚠️ The kaiHEN README warns that homebrew gets full system/NAND access and that malicious or buggy homebrew can brick the console.

## 3. Starting point for the code

Don't start from upstream Dolphin. Fork **dolphin-nx** (https://github.com/NaGaa95/dolphin-nx), a Switch 1 port
that is synced with upstream and actively maintained (v1.2.2, 2026-11-13). It already has:
- a libnx build (libounce is a drop-in replacement for libnx),
- a Vulkan backend on **NVK/Mesa** (OunceVK is also NVK, so the GPU path is close to identical),
- the libnx `Jit` API for the AArch64 JIT,
- an SDL launcher, game library, gyro/motion input, DSP HLE fixes and fastmem reservation work.

Before forking, read its `COPYING` file: sources disagree on GPL-2.0+ vs GPL-3.0. Dolphin upstream is GPLv2+.

## 4. Porting steps

1. **Bring up the toolchain.** Build and run the ounce-devkit `examples/` (Vulkan and GLES) on the console through kaiHEN.
2. **Make a JIT smoke test.** Write a tiny NRO that does `jitCreate` → write a few AArch64 instructions → `jitTransitionToExecutable` → call them.
   This proves the kaiHEN JIT path before any Dolphin code is involved.
3. **Retarget the build.** In dolphin-nx, replace the libnx rules/toolchain with `$DEVKITPRO/libounce/switch2_rules`
   or `switch2vars.sh` for CMake, and link `-lvulkan` from OunceVK instead of the Switch 1 Mesa build.
   Drop Switch-1-only pieces such as Deko3D and the SaltyNX hooks.
4. **Adapt the JIT to kaiHEN's semantics.** This is the biggest technical risk.
   - kaiHEN uses dual mapping: you write to an RW *staging* buffer, and RO copies it into the RX view. No RWX memory exists.
   - A plain `jitTransitionToExecutable` copies the **entire** buffer. Dolphin emits small blocks constantly,
     so switch to `kaihenJitPublishRanges` (sparse publish) or performance will collapse.
   - Staging roughly doubles the physical memory the code cache uses. There is a limit of 512 live mappings per session.
   - Cross-core icache invalidation is **not** synchronized for you. Dolphin's block-unlinking and invalidation must
     make sure that no thread runs a block while it is being rewritten.
   - Check how Dolphin's `JitArm64` already handles separate write and execute views (it does this for macOS W^X)
     and reuse that path.
5. **Fastmem.** Dolphin's fastmem reserves a large virtual address range and relies on catching memory faults.
   Fault handling and large address-space reservations on Switch 2 are undocumented, so ship with **fastmem off** first
   and get it working afterward.
6. **Graphics.** Vulkan backend via `VK_NN_vi_surface` on `nwindowGetDefault()`. No Vulkan loader exists, so resolve
   extensions with `vkGet*ProcAddr`. Redirect Mesa logs: `freopen("sdmc:/log.txt","w",stderr)`.
   Test shader compile stutter and enable ubershaders or async shaders.
7. **Threads and memory.** Switch 2 has an 8-core ARM Cortex-A78C CPU (6 cores reportedly available to games) and 12 GB of RAM.
   The share homebrew can use under kaiHEN is undocumented. Measure it, then tune Dual Core mode and core masks
   (`svcSetThreadCoreMask`) for the CPU, GPU and audio threads. Prefer application mode (title takeover) over applet mode
   to get full memory.
8. **Audio, input and storage.** Check that libounce's audren/audout, HID (Joy-Con 2 and Pro Controller, SixAxis gyro for
   Wii pointer and tilt) and SD (`sdmc:`) behave as they do on libnx. Fix whatever doesn't.
9. **Package and test.** Build `dolphin.nro` and add it to `/switch/dolphin/`. Test with legally dumped games, starting with lightweight 2D and early GameCube titles.

## 5. Open questions to answer on hardware
- How much RAM can a kaiHEN NRO use, and how many cores?
- Does devkitA64's libstdc++ fully support exceptions and RTTI with libounce? (Dolphin uses both lightly.)
- What does the publish IPC cost per JIT block? This decides how Dolphin should batch publishes.
- Can a process install exception handlers for fastmem faults?
- Which Vulkan extensions and features does OunceVK expose? Run a `vulkaninfo`-style dump.
